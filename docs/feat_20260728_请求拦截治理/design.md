# 请求拦截治理 —— 设计

> 状态：待评审
> 分支：`feat_20260728_请求拦截治理`

## 1. 背景

当前 wandkit 的能力边界等于**声明过的工具集合**：没写 `defineWriteTool`，Agent 就做不了那件事。这带来两个后果：

- **接入成本高。** 每一项能力都要写 schema、风险等级、`prepare`/`execute`。
- **覆盖必然有缺口。** 宿主自有代码、以及未来任何非声明式执行路径产生的写操作，完全在治理之外。

同时，风险分类当前**只能**来自工具契约的 `risk` 字段。这让「能力声明」和「风险分类」这两件本来独立的事被绑死——而它们不必绑死。

本设计拆开这两个角色：

| 角色 | 现在 | 改造后 |
|---|---|---|
| **能力发现** | 声明式（glob 扫文件 + 工具清单） | **自动化**（可访问性树 + 路由表 + 请求观测），见 §4.3 |
| 能力执行 | 仅限已声明工具 | 通用 DOM 原语，声明式工具降为可选精确路径 |
| 风险分类 | 来自 `risk` 字段 | 来自**请求层判定策略**（默认拒绝 + 名单 A/B） |

目标：**广度与安全不再互斥**。Agent 能做没声明过的事，而这些事照样过闸门。

三者是同一件事的三个面：不声明也能**发现**能力，不声明也能**执行**，而无论怎么来的写操作都在请求层被**统一治理**。

## 2. 定位变更（需要明确承认）

README 现有的非目标声明将被推翻：

```diff
- 不解析 DOM、不模拟点击——那是执行引擎的事
+ 提供通用 DOM 操作原语（@wandkit/executor），能力不再需要逐个声明
```

项目从「纯治理层」扩展为「治理层 + 可选执行层」。**治理仍是核心**：`@wandkit/executor` 是独立可选包，不装它时行为与现在完全一致。

## 3. 总体架构

```
                    ┌─────────────────────────────────┐
   用户输入 ──→     │        AgentRuntime (core)       │
                    └────────┬───────────────┬─────────┘
                             │               │
              路径 A：声明式工具         路径 B：通用 DOM 原语
                             │               │
                    prepare → 确认 → execute │  read/click/input/…
                             │               │
                             ↓               ↓
                    ┌────────────────────────────────┐
                    │   @wandkit/interceptor      │
                    │   fetch / XHR / sendBeacon      │
                    │   默认拒绝 + 名单 A/B            │
                    └────────────┬───────────────────┘
                                 ↓
                          确认卡片（复用 ui 包）
                                 ↓
                          放行 / 拒绝
```

两条路径**强度不同，必须在文档里显式区分**：

| | 路径 A（声明式工具） | 路径 B（通用原语 + 拦截） |
|---|---|---|
| 强制力 | 类型层面（`execute` 拿不到 `TInput`） | 运行时 |
| 确认时机 | 动作**之前** | 动作**中途**（发请求那一刻） |
| 确认前重跑比对（TOCTOU） | 有 | 无 |
| 披露内容 | 业务语义（「用户：张三」） | 原始请求（可选 `describe()` 富化） |
| 覆盖面 | 仅已声明工具 | 一切走网络的写 |

定位是**纵深防御**：A 精确制导，B 兜底渔网。B 的存在让 A 的覆盖缺口不再致命。

## 4. 能力去声明化

### 4.1 已否决：`ExecutorPort` 端口式执行器

初版设计提出一个窄端口，接 page-agent 这类外部执行引擎：

```ts
interface ExecutorPort {
  execute(instruction: string, signal?: AbortSignal): Promise<ExecutorResult>
}
```

**已否决。** 这个签名（一句话进、结果出）恰恰是为「整包接入一个自带 Agent 循环的
执行器」设计的，而那正是 dom-capture.md §7 明确不采纳的做法——page-agent 自带完整
LLM 循环，接进来会与 `AgentRuntime` 已有的循环**叠成两层**，轮次上限、`maxToolCalls`、
trace、超时预算全部失效。中间发生了什么，运行时完全看不见。

### 4.2 采用：通用 DOM 原语

同一个目标由 `@wandkit/executor` 达成，形态完全不同：

| | `ExecutorPort`（否决） | 通用原语（采用） |
|---|---|---|
| 接口 | 一句话进 → 结果出 | `read` / `click` / `input` / `select` / `scroll` |
| 循环在哪 | 执行器内部 | **`AgentRuntime` 的循环** |
| 运行时可见性 | 只看得到最终结果 | 每一步都过工具调用 |
| 轮次上限 / trace / 闸门 | 失效 | 全部生效 |

接入方声明的是 5 个原语，而不是 N 个业务动作；声明一次之后，Agent 能做的事等于用户
在界面上能做的事。**能力不再需要枚举**，这正是「去声明化」的原意，且不必付出双层
循环的代价。

已在真实后台（aicc-admin-front）跑通：Agent 读页面 → 按索引点击 → 重读确认，全程
经由 `AgentRuntime`。

> `defineExecutorTool` 的骨架随之删除。它此前因「核心包 `ToolRisk` 放不下无法预判
> 风险的工具」而阻塞（见 §4.6），该阻塞一并消失——原语是普通的 `read` 工具，其副作用
> 由请求层拦截逐个定级。

### 4.3 自动化能力发现：无状态逐步重读（采用 page-agent 模式）

**不维护任何能力目录。每一步动作前重新读取当前 DOM。**

#### 被否决的方案：目录式发现

初版设计曾提出三探针（可访问性树 + 路由表 + 请求观测累积成 API 目录）。**已否决**，原因如下：

| 问题 | 说明 |
|---|---|
| **错误的抽象** | API 目录服务的是名单判定，不是 Agent 的行动。Agent 点的是按钮不是端点，给它 `DELETE /api/users/:id` 它也不知道该点哪里 |
| **必然漂移** | SPA 的可操作项随数据、权限、组件状态变化，任何缓存目录立刻过时 |
| **权限错配** | 目录是全集，当前用户实际可见的是子集 |
| **冷启动为空** | 累积式观测首次运行什么都没有 |
| **归一化不可靠** | 从 `/api/users/u_1` 猜出 `/api/users/:id` 只能靠启发式，且会猜错 |

一个需要靠猜的机制，不该出现在治理链路里。

#### 采用的方案

每次规划动作前调用一次「读取当前页」，产出简化的可交互元素列表交给模型：

```
循环：读取当前页 → 模型选择动作 → 执行 → 再读取
```

优点是前一节那五个问题全部消失：永远是当前真相、天然匹配当前用户权限、无冷启动、无归一化。代价是每步多一次 DOM 序列化，属可接受成本。

模型本就擅长从文本里定位目标，无需预先结构化成目录——这也是 page-agent 明确宣称 "reads the live DOM as text" 的原因。

#### 读取内容的硬约束

只允许取生产构建后仍然存在的信息，见 §4.4：**可交互元素的 `role`、可访问名、原生属性、文本内容**。禁止 CSS class、组件名、DOM 结构路径。

#### 与治理层正交

发现方式换成逐步重读，**不影响**拦截器：

```
发现（DOM，动作前）   ——  Agent 知道能点什么
治理（请求，动作中）  ——  闸门知道会发生什么
```

两者不共享状态、不互为前提。这一点必须保持——**page-agent 本身没有确认机制**（README / README-zh / AGENTS.md 三份官方文档均未描述确认、授权或危险动作防护）。采纳它的发现方式，不等于采纳它的安全模型。

#### 仍然无法自动发现的：领域知识

以下几项**原理上不可能**从运行时探测出来，它们是人类知识而非系统事实：

| 项 | 为何测不出 | 处置 |
|---|---|---|
| 字段语义、消歧规则 | 「状态=2」是什么意思，页面上没写 | 可选注入，缺失则模型自行推断 |
| 业务约束 | 「退款超 500 需主管审批」 | 可选注入 |
| 后果严重性 | 删一条测试数据 vs 删一个客户 | 名单 B 人工标注 |

结论：**发现全自动，知识可选注入**。不注入也能跑，注入则质量更好——与 `prepare` 的定位一致（可选的质量升级，而非前置门槛）。

### 4.4 生产构建下的能力发现（硬约束）

执行器要在**生产构建后**认得出页面上有什么。实测（esbuild minify + Vite production build）结论：

| 线索 | 构建后 | 可用 |
|---|---|---|
| 组件 / 函数名 | `DeleteUserButton` → `t` | ❌ 蒸发 |
| CSS class | `dangerButton` → `_dangerButton_wukff_1` | ❌ 哈希化 |
| 文本内容 | `删除用户` 原样 | ✅ |
| ARIA（`role` / `aria-label`） | `删除用户 张三` 原样 | ✅ |
| 原生属性（`name` / `placeholder` / `type`） | 原样 | ✅ |

**因此执行器的能力发现只允许建立在可访问性层**：文本、ARIA 语义、原生属性。禁止依赖 CSS class、组件名或 DOM 结构路径——它们在生产构建后要么不存在，要么随每次构建变化。

#### 补充：无语义元素靠 `cursor: pointer` 兜底

真实浏览器实测（aicc-admin-front，Element UI 2.15）发现纯语义选择器有覆盖缺口：**下拉浮层的选项是纯 `<li>`，既无 `role` 也无 `tabindex`，一个都抓不到**。

解法是 `cursor: pointer`，它是本方案里唯一可靠且框架无关的补充信号：

| 元素 | 实测 `cursor` |
|---|---|
| 下拉选项 `<li>` | `pointer` |
| 表格操作按钮 | `pointer` |
| 普通文本 | `auto` |

它之所以合格，恰恰满足前面那条硬约束：**它是计算样式，即浏览器渲染后的事实，不是类名**。构建工具哈希的是类名，样式值本身不受影响；而任何 UI 库把某个东西做成可点的都会给它 `pointer`，否则用户根本看不出那里能点。

> 早期曾用 `.el-select` 一类框架类名做适配，**已废弃**——它违反本节原则，且换个 UI 库即失效。

去重是必需的：`cursor` 向下继承，`<button><span>删除</span></button>` 会产出两条同名记录。三条排除规则只作用于 cursor 路径（祖先已是语义可交互元素、自身含语义可交互后代、还有更内层的可点元素），语义标签不受影响。

#### 由此得到的推论：不必预判组件类型

Element UI 的 `<el-select>` 渲染成 `<input readonly>`，原始 DOM 里**没有任何信息**能把它与「只读展示字段」区分开——该库不提供 ARIA。

但**逐步重读模式让这个区分变得不必要**：快照只陈述事实（只读、不可输入），Agent 据此知道唯一能做的是点击；点开后重读页面，选项已成为普通可点元素。组件类型是被**经验发现**的，不是被预先声明的。

这是无状态重读相对目录式发现的又一处优势，也是不需要任何框架知识的根本原因。

这与本仓库 E2E 选择器规则同源（优先 `getByRole` / `getByLabel`，禁止易变 class），也解释了 page-agent 为何强调 "reads the live DOM as text"。

**必须写进接入文档的代价**：非声明式发现的质量取决于宿主应用的可访问性水平。若按钮只有 `<button class="_x1y2">` 而无可访问名称，执行器就发现不了它。此时「去声明化」并未真正降低接入成本，只是把成本从「写工具声明」转移到「补 a11y 语义」——区别在于后者对产品本身也有价值，而前者只服务于 Agent。

> 注：声明式路径不受此影响。工具的 `moduleId` / `aliases` / `risk` 等是**数据而非标识符**，属性名默认不被 mangle，中文字面量仅做 ASCII 转义（`用户` ≡ `"用户"`），glob keys 也以字面量烘焙进产物——三者均已实测验证。

### 4.5 权限

DOM 原语与普通工具一样受权限过滤。没有对应权限的用户，模型根本看不到这些原语——最小权限原则在这一层仍然成立。

### 4.6 移除 `ToolRisk`：风险分类改由名单单一提供

**结论：删除 `risk` 字段，不是给它加一档。**

#### 为什么原设计必须被打破

现有 `risk` 是**自声明且无法验证**的。README 自己承认：

> Runtime 从不推断风险。一个真会改数据却声明成 `read` 的工具会绕过确认

于是「靠类型，不靠自觉」只成立一半：类型能防「已正确标注为 write 的工具漏掉两阶段拆分」，防不住「标错」。一个偷偷写库的 `read` 工具是**静默绕过闸门**的，没有任何测试能抓到。

名单方案把分类依据从「作者声明时的猜测」换成「请求发出时的事实」——即本包既有的 `rawRequest` 原则（唯一不可能撒谎的部分）往上提一层。

#### `risk` 四项职责的新归属

| 原职责 | 新归属 |
|---|---|
| 要不要确认 | 名单（按真实请求判定） |
| 卡片轻重（`destructive`） | 名单 B |
| 调度走 `prepare` 还是直执行 | **工具结构**——有无 `prepare`，无需 `risk` |
| `navigation` 视口接管 | `executionMode: 'page'` 已覆盖，本就冗余 |

四项均有更合适的归属，字段整个删除。

#### `prepare` / `execute` 保留，但改变定位

两阶段拆分与名单解决的**不是同一个问题**，不应一并删除：

| | 名单 | `prepare` / `execute` |
|---|---|---|
| 回答什么 | 这次危不危险 | 何时问人、给人看什么 |
| 确认时机 | 请求发出那一刻 | 动作**之前** |
| 披露 | 原始 HTTP | 业务语义 |
| TOCTOU 重跑比对 | 无 | 有 |

**倒转权威，而非二选一：**

- **名单是权威**：决定要不要确认、多重。对声明式工具与自由执行一视同仁。
- **`prepare` 是可选的披露质量升级**：写了能在动作前用业务语言问；不写也拦得住，只是卡片是原始请求。

激励方向由此摆正——写 `prepare` 是为了**体验更好**，而不是为了**不被漏掉**；后者由名单无条件保证。

#### 两条路径的接缝：`rawRequest` 作为连接键

`prepare` 声明「我将发出 `DELETE /api/users/u_1`」→ 用该**预测请求**匹配名单，动作前即可定级；请求真正发出时，拦截器再匹配一次真实请求。

**两次定级不一致，即「工具声明与实际行为不符」，直接判失败。** 这把「标错风险」从一个查不出的静默洞，变成一条硬失败——原设计做不到这件事。

#### 强制前置依赖

名单成为唯一分类来源后，**未安装拦截器 = 完全没有治理**。必须在 `ToolRegistry` 构造期强制校验并抛错，与本包既有风格一致（契约违规在应用启动前就炸，而不是在生产环境表现为一次错误写入）。

#### 爆炸半径

这是核心契约的破坏性重构，非增量：

| 影响面 | 程度 |
|---|---|
| `ToolRisk` / `ToolDefinition` 联合类型 | 删除重写 |
| `defineReadTool` / `defineWriteTool` / `defineNavigationTool` | API 变更 |
| `ToolRegistry.assertExecutionContract` | 整段重写 |
| `AgentRuntime` 全部 `tool.risk === ...` 分支 | 重写 |
| 现有 234 单测 | 约 60~80 条需重写 |
| README 核心设计 §1 §2 | 重写 |
| 拦截器 | 由「可选兜底」升为**必需组件** |

属 1.0 级别的重新定位，需明确授权后执行。

## 5. 拦截器

### 5.1 判定策略

```ts
type Verdict =
  | { action: 'allow' }
  | { action: 'confirm', risk: 'write' | 'destructive' }
  | { action: 'deny', reason: string }
```

判定顺序（**顺序本身是安全语义，不可调整**）：

| 序 | 条件 | 结果 | 理由 |
|---|---|---|---|
| 1 | 非 Agent 发起 | `allow` | 用户自己的操作不归闸门管 |
| 2 | 处于已授权窗口 | `allow` | 路径 A 已确认过，见 §7 |
| 3 | 命中**名单 B（danger）** | `confirm` as `destructive` | **必须先于名单 A，也先于安全方法放行** |
| 4 | 安全方法（GET/HEAD/OPTIONS/TRACE） | `allow` | 无副作用 |
| 5 | 命中**名单 A（allow）** | `allow` | 已知安全的写 |
| 6 | 兜底 | `confirm` as `write` | **默认拒绝** |

**第 3 步为何要先于第 4 步**（实现阶段修正的排序）：GET 并非总是安全——`GET /api/export-all-data` 这类导出接口没有副作用却会外泄数据。若安全方法先短路，这类请求将永远无法被名单拦下。把危险名单提前，既保住「GET 默认廉价放行」，又留出显式拦截危险读的能力。

**第 3 步先于第 5 步是本设计最关键的一条。** 名单 A 往往写成宽泛通配（`POST /api/*/search`），若让它先匹配，一条粗糙的放行规则就可能把高危动作一并放过。危险优先于放行，是安全策略的通例。

**第 6 步是与「黑名单」的根本区别。** 新上线的 `/api/v2/purge` 没人加进名单，仍然会被拦下要求确认——漏配的代价是多一次确认，而不是静默失去防护。

### 5.2 规则与匹配

```ts
interface RequestMatcher {
  method?: string | string[]
  /** glob（支持 * 与 :param）或 RegExp */
  url?: string | RegExp
  /** 进一步按请求体判定，如仅当 { force: true } 才算高危 */
  when?(request: InterceptedRequest): boolean
}

interface RequestRule {
  id: string
  match: RequestMatcher
  /** 可选：把原始请求翻译成业务语义，见 §6 */
  describe?(request: InterceptedRequest): Promise<RequestDisclosure>
}
```

### 5.3 拦截通道

| 通道 | 可否挂起 | 处理 |
|---|---|---|
| `fetch` | 可 | 等判定后再调原始实现 |
| `XMLHttpRequest` | 可（`send` 内部延迟透传） | 同上，但破坏同步时序，需记录为已知限制 |
| `navigator.sendBeacon` | **不可**（设计为 unload 期发送，同步返回 boolean） | 命中需确认时**直接拒发并返回 false**，并告警 |
| `<form>` submit | 可（capture 阶段 `preventDefault`） | 确认后再程序化提交 |
| `<a href>` 导航 | 不适用 | 属导航非写入，不拦 |
| WebSocket / SSE | 本期不覆盖 | 记入已知缺口 |

`sendBeacon` 是真实缺口：无法挂起，只能二选一（放行或拒发）。默认拒发更符合本包的立场，但会改变宿主行为，需在文档中显著提示。

### 5.4 生命周期

```ts
interface Interceptor {
  install(): () => void   // 返回 uninstall，可重复调用且幂等
}
```

必须可卸载（测试、SPA 热更新），且对未被拦截的请求保持原始行为与原始 `this` 绑定。

## 6. 归属判定

拦截器必须分清 Agent 发起与用户发起，否则用户手动点删除也会弹确认，产品不可用。

```ts
interface AttributionPort {
  isAgentActive(): boolean
}
```

默认实现绑定 `@wandkit/ui` 的 `InteractionMask`：遮罩武装期间即 Agent 动作窗口。这是**排除法**——窗口内用户无法操作，故请求必然来自 Agent，从而绕开了「跨异步边界传递发起方上下文」这个浏览器里没有可靠解法的问题。

**宽限期**：Agent 动作可能触发防抖保存等延迟请求，在遮罩解除后才发出。设 `graceMs`（默认 500ms），解除后该窗口内仍按 Agent 归属。取值需权衡：过长会把用户的操作误判成 Agent 的。

## 7. 双路径去重（必做项，非优化）

路径 A 的工具在用户确认后执行 `execute`，其内部发出的请求会被拦截器再次捕获。若不处理，**每给一个动作写声明式工具，反而多挨一次确认**——等于惩罚正确做法。

方案：**已授权窗口**。

```ts
interface AuthorizationScope {
  begin(token: string): void
  end(token: string): void
}
```

`ActionRouter` 在执行已确认的写工具前后调用。窗口内的 Agent 请求视为已获批准，直接放行，但**仍写入 trace**。

**已知取舍**：窗口是粗粒度的——该工具在窗口内发出的任何请求都会被放行。这在路径 A 的信任模型下可接受（工具是声明过、评审过的代码，其行为本就被假定与声明一致），但必须在文档中写明：**它不防御「声明式工具本身行为不符合声明」这种情况**。

## 8. 披露

路径 B 天然只有原始请求。`PreparedAction.rawRequest`（已实现）正是为此准备的字段，直接复用。

```ts
interface RequestDisclosure {
  title: string
  rows: ConfirmationRow[]
  impact?: string
}
```

不提供 `describe()` 时，卡片展示 `method + url + body`。这**确实是相对路径 A 的能力下降**——给人看 `DELETE /api/users/u_1`，他得自己知道 u_1 是张三。

缓解：按规则可选注册 `describe()`。它是**可选增强**而非前置门槛，因此不会把「逐个声明」重新变成必需品。

## 9. 安全性分析

### 9.1 相对现状增强

- 宿主自有代码、未声明能力产生的写入，**首次**进入治理范围。
- 漏配规则的后果从「静默无防护」变为「多一次确认」。

### 9.2 相对现状削弱

| 削弱项 | 说明 |
|---|---|
| 确认时机后移 | 从「动作前」变成「请求发出那一刻」。用户拒绝时，页面可能已被填了一半，需要执行器负责回退或明确终止 |
| 无 TOCTOU 重跑比对 | 请求体已冻结，但它要作用的数据仍可能在确认期间被改动，且拦截器无法重跑 `prepare` 去比对 |
| 披露质量 | 见 §8 |

### 9.3 新增攻击面

- **Prompt injection 面显著扩大。** DOM 原语把整页可交互元素读进快照，比带 schema 的声明式工具暴露得多。现有缓解（页面上下文以 user 角色注入并标注不可信）在这里**强度不足**——注入内容可以直接是「点击那个删除按钮」这类可执行指令。这是本设计最需要正视的风险，拦截器的默认拒绝正是针对它的最后一道防线。
- **客户端副作用不经网络**（清 localStorage、纯前端状态变更后批量保存），拦截器看不见。

## 10. 不做什么

- 不做后端侧鉴权。后端始终是每次调用的最终裁决方，本设计只解决「浏览器内、Agent 发起」这一段。
- 不保证拦截无法被绕过。宿主页面自身的代码若直接持有原始 `fetch` 引用，可绕开 patch。本设计防的是 Agent 的误操作，不是恶意宿主。
- 本期不覆盖 WebSocket / SSE / Service Worker。
