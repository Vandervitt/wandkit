## 关于能力发现

**已否决目录式发现，改用 page-agent 的无状态逐步重读**（design §4.3）。

因此**没有独立的发现阶段**——发现由执行器在每步动作前自行读取当前 DOM 完成，属阶段 5 适配器的内部行为，不需要本包维护任何目录、归一化逻辑或累积状态。

原计划中「path 归一化」这一核心难点随之消失：它只在维护 API 目录时才需要，而目录已被否决。名单判定是拿**实际到来的请求**去匹配人工书写的模式，从不需要反向推断模式。

阶段 3 的「已授权窗口」是**必做项**，不是优化：不做则每写一个声明式工具反而多一次确认。

## 阶段 1 测试矩阵（判定顺序）

按 design.md §5.1 的六条，每条至少一例，另加边界：

| # | 场景 | 期望 |
|---|---|---|
| 1 | 非 Agent 发起的 DELETE | `allow` |
| 2 | 已授权窗口内的 POST | `allow` |
| 3 | Agent 发起的 GET | `allow` |
| 4 | 同时命中名单 A 与名单 B | `confirm` as `destructive`（**B 优先**） |
| 5 | 仅命中名单 A 的 POST | `allow` |
| 6 | 未命中任何名单的 PUT | `confirm` as `write`（默认拒绝） |
| 7 | 名单 B 的 `when()` 返回 false | 退回后续判定，不强判 destructive |
| 8 | 未知方法（如 `PROPFIND`） | 按非安全方法处理 → `confirm` |

第 4 条是核心回归用例，必须显式覆盖——它守的是「宽泛放行规则不得盖过高危规则」。

### 实施后补充的用例

实现阶段发现两处原矩阵未覆盖、但影响安全语义的点，已补：

| # | 场景 | 期望 | 为什么重要 |
|---|---|---|---|
| 9 | 危险名单命中 GET | `confirm` as `destructive` | 导出类接口无副作用却外泄数据；据此把 `danger_list` 提到 `safe_method` 之前 |
| 10 | 危险规则 `when()` 抛错 | 视为**命中** | 规则写坏不得导致高危动作被放过 |
| 11 | 放行规则 `when()` 抛错 | 视为**未命中** | 同上，两个方向都朝「更需要确认」倒 |
| 12 | 规则求值异常上报 | 触发 `onRuleError` | 一直抛错的规则会持续偏移判定，不能静默 |
| 13 | glob `*` 不跨 `/`、`**` 跨 `/`、整体锚定、元字符转义 | 各自钉死 | 直接决定放行规则的真实覆盖面 |

## 风险与对策

| 风险 | 对策 |
|---|---|
| `sendBeacon` 无法挂起 | 默认拒发 + 告警；文档显著提示 |
| XHR 同步时序被破坏 | 记为已知限制，提供 `passthrough` 逃生配置 |
| 宽限期误判用户操作为 Agent | `graceMs` 默认取小（500ms），可配 |
| 已授权窗口过粗 | 文档写明不防御「工具行为不符合声明」 |
| Prompt injection 面扩大 | 默认拒绝兜底；执行器工具须可被权限过滤 |
| 拦截器可被绕过 | 明确非目标：防误操作，不防恶意宿主 |

## 阶段 2 实施记录

三条通道的难点各不相同：

| 通道 | 处理 | 代价 |
|---|---|---|
| `fetch` | 判定后再调原始实现 | 无 |
| `XMLHttpRequest` | `open` 记录、`send` 内部延迟发送 | **破坏同步时序**，见下 |
| `sendBeacon` | 无法挂起，需确认时拒发并回调告警 | 改变宿主既有行为 |

`form` 提交本期未做——需显式开启且与宿主表单逻辑耦合较深，留待有真实场景时再补。

### XHR 的已知限制

`send()` 必须同步返回，而判定是异步的，因此真正的发送被推迟到判定落地之后。依赖
「`send` 返回即已发出」的宿主代码会看到时序变化。这是本方案无法消除的代价，已写成
一条显式用例钉住行为，而不是留在文档里。

另一处不对称：fetch 被拒时抛 `RequestDeniedError`，XHR 被拒时**什么也不做**——它没有
可以抛错的返回值，宿主的 `error` / `timeout` 处理都不会被触发。

### 三条实现纪律的落实

1. **未命中原样透传**——保留 `this` 绑定、参数原样转发、返回值不包装。
2. **闸门自身出错时从严**——归属判定抛错按「Agent 发起」处理，策略求值抛错按「需要
   确认」处理，`confirm` 回调抛错按「拒绝」处理。三处都朝更安全的方向倒。
3. **拒绝给出可分辨的失败**——`RequestDeniedError` 而非普通 Error，调用方据此区分
   「被用户拒了」与「网络挂了」。与核心包用 `cancelled` 标记而非文案判定取消同源。

唯一的例外是 `describe()` 抛错：只降级卡片质量，不连带拒掉请求——那会把一个可用的
确认流程变成死路。


## 阶段 3 实施记录

### 已授权窗口用按 token 的计数

不用布尔量，也不用单一总数，而是 `Map<token, count>`：

- **布尔量**：一个工具的 `execute` 内部再触发嵌套的已授权操作时，内层的 `end` 会把
  外层窗口一起关掉，外层剩余请求于是重新开始弹卡片。
- **单一总数**：`end` 一个从未 `begin` 过的 token 会把别人的窗口关掉；重复 `end`
  还会把计数压成负数，导致下一次 `begin` 之后仍判为未授权——闸门在本该放行时拦人。

`runAuthorized` 的 `end` 放在 `finally` 里。`execute` 抛异常却没关窗口，后续所有
Agent 请求都会被无条件放行，**而且不会有任何报错提示闸门已经失效了**。

### 归属判定的宽限期

Agent 的操作常触发防抖保存一类的延迟请求，它们在遮罩解除之后才真正发出。不留宽限期
的话这些写入会被当成用户自己的操作直接放行。

取严格小于（`now - lastArmedAt < graceMs`），使 `graceMs` 成为「不再算 Agent」的
那一刻。重新武装会刷新起点。

遮罩状态读取抛错时按「Agent 发起」处理——宿主的遮罩实现出错，不该导致写操作被静默
放行。

### 与真实 InteractionMask 的联调

归属判定的整条依据建立在遮罩上，因此单测里接了 `@toolairlock/ui` 的真实实现，确认
`armed` 属性与本包假设一致。只测自己造的假遮罩，等于没测这条依据。

### 样例覆盖的五个场景

`npm run example:interceptor` 实跑通过：

| 场景 | 结果 |
|---|---|
| 用户自己点的删除 | 放行，不打扰 |
| Agent 发起同样的删除 | 命中危险名单，确认 |
| 已授权窗口内两次写操作 | **确认 0 次** |
| 放行名单宽泛 vs 危险名单 | 危险优先，没被盖住 |
| 谁都没命中的新接口 | 默认拒绝，要确认 |

第三条是阶段 3 的核心判据：不做这个，接入方每写一个声明式工具反而多挨一次确认。


## 阶段 4 实施记录

### 接线层刻意很薄，但不能没有

拦截器**故意不依赖 UI 包**（它要能在没有界面的场景下单独治理宿主代码），而确认卡片
需要 `confirmationId` 与 `rawRequest`——两者都不在 `RequestDisclosure` 里：前者由接线
层生成，后者直接取自被拦下的请求。

### 独立子入口：`@toolairlock/interceptor/confirm-ui`

实施中踩了一个坑：最初把 `createConfirmCardHandler` 从主入口 re-export，结果**任何
一次 `import { createInterceptor }` 都会连带拉进 `@toolairlock/ui`**，而那个包在模块
顶层就 `extends HTMLElement`——在没有 DOM 的环境里直接崩。

「拦截器可脱离界面单独使用」这条设计就此作废，而且崩得莫名其妙（报错指向 UI 包，
但用户根本没导入它）。

改为独立子入口，并补了一条测试守住主入口的导出面。

### 其余取舍

- **逐个确认，不同时堆两张卡片**——堆在一起会让人分不清自己批的是哪一个，审计记录
  也说不清。与核心包 `ConfirmationManager` 的取舍一致。
- **过期 ID 的决定被忽略**——上一次遗留在屏幕上的卡片回传旧 ID，放行它等于用旧的
  同意批准这一次。
- **确认期间自动解除遮罩**——遮罩挡的是「用户操作页面」，而确认卡片恰恰**需要**
  用户点击，不解除就点不到自己的闸门。决定后恢复；确认前本就未武装时不误开。
- **没有披露信息时退化为原始请求**——`describe()` 是可选增强，缺了它只是卡片难看些，
  不该让确认流程走不下去。

### 样例第六幕

`npm run example:interceptor` 现在跑完六个场景，最后一幕接真实卡片：

```

标题: 确认删除客户

>> 用户点击卡片上的【拒绝】
确认结果: false   ← 请求不会发出
```


## 阶段 5（原 ExecutorPort）已否决

原计划接一个窄端口 + page-agent 适配器，让 Agent 能做没声明过的事。

**否决理由**：该端口的签名（一句话进、结果出）是为「整包接入自带 Agent 循环的执行器」
设计的，而那与 `AgentRuntime` 已有的循环会叠成两层——轮次上限、`maxToolCalls`、trace、
超时预算全部失效。这条在 dom-capture.md §7 就已明确不采纳，端口设计与它自相矛盾。

**目标已由 `@toolairlock/executor` 达成**：5 个通用 DOM 原语（read / click / input /
select / scroll），循环仍在 `AgentRuntime` 手里，每一步都过工具调用，因此轮次上限、
trace、闸门全部生效。已在真实后台跑通。

连带解除的阻塞：`defineExecutorTool` 此前因核心包 `ToolRisk` 放不下「无法预判风险的
工具」而卡住（design §4.6），骨架删除后该阻塞消失——原语是普通 `read` 工具，其副作用
由请求层拦截逐个定级。


## 阶段 5 实施记录

### trace 记录器同样不 import 核心包

用最小鸭子类型描述 `TraceCollector`，与 bridge、attribution 的做法一致——拦截器要能
在没有 Agent 运行时的页面上单独使用。`getRunId()` 返回 `undefined` 时跳过记录而非
报错，正是为了这个场景。

### 放行也记录

只记拦下的，等于把闸门最常走的那条路径变成盲区。审计需要能证明「这次没拦」是有依据
的——事件里带着命中的规则 ID。

### 脱敏比核心包更严

| 项 | 处置 |
|---|---|
| URL query | **剥掉**——常带 token 与手机号 |
| origin | 剥掉——对审计无鉴别力且更长 |
| 请求体 | **完全不进轨迹**——最容易带敏感数据 |

核心的 `TraceCollector` 连用户原话都只存长度（`[redacted:length=N]`），判定轨迹没有
理由更宽松。而轨迹默认会落到 localStorage。

### README 定位改写

原文那句「不解析 DOM、不模拟点击——那是执行引擎的事」已经不成立（executor 包提供了
DOM 原语），「不提供聊天 UI」同样过时（chat 包）。

改写为**核心包不做什么 + 生态提供什么**两节：三条非目标对核心包永远成立，需要那些
能力时装对应的独立包。并新增「两条治理路径」对照表，让接入方看得见 A 与 B 的强度
差别——拆成独立包不是为了模块化好看，而是因为强度真的不同。

顺带订正一处数字：README 曾把全仓单测数写进核心包（234 vs 实际 210），改为分开表述。
