## 关于能力发现

**已否决目录式发现，改用 page-agent 的无状态逐步重读**（design §4.3）。

因此**没有独立的发现阶段**——发现由执行器在每步动作前自行读取当前 DOM 完成，属阶段 5 适配器的内部行为，不需要本包维护任何目录、归一化逻辑或累积状态。

原计划中「path 归一化」这一核心难点随之消失：它只在维护 API 目录时才需要，而目录已被否决。名单判定是拿**实际到来的请求**去匹配人工书写的模式，从不需要反向推断模式。

阶段 3 的「已授权窗口」是**必做项**，不是优化：不做则每写一个声明式工具反而多一次确认。

## 阶段 1 测试矩阵（判定顺序）

按 design.md §5.1 的六条，每条至少一例，另加边界：

| # | 场景 | 期望 |
|---|---|---|
| 1 | 非 Agent 发起的 DELETE | `allow` |
| 2 | 已授权窗口内的 POST | `allow` |
| 3 | Agent 发起的 GET | `allow` |
| 4 | 同时命中名单 A 与名单 B | `confirm` as `destructive`（**B 优先**） |
| 5 | 仅命中名单 A 的 POST | `allow` |
| 6 | 未命中任何名单的 PUT | `confirm` as `write`（默认拒绝） |
| 7 | 名单 B 的 `when()` 返回 false | 退回后续判定，不强判 destructive |
| 8 | 未知方法（如 `PROPFIND`） | 按非安全方法处理 → `confirm` |

第 4 条是核心回归用例，必须显式覆盖——它守的是「宽泛放行规则不得盖过高危规则」。

### 实施后补充的用例

实现阶段发现两处原矩阵未覆盖、但影响安全语义的点，已补：

| # | 场景 | 期望 | 为什么重要 |
|---|---|---|---|
| 9 | 危险名单命中 GET | `confirm` as `destructive` | 导出类接口无副作用却外泄数据；据此把 `danger_list` 提到 `safe_method` 之前 |
| 10 | 危险规则 `when()` 抛错 | 视为**命中** | 规则写坏不得导致高危动作被放过 |
| 11 | 放行规则 `when()` 抛错 | 视为**未命中** | 同上，两个方向都朝「更需要确认」倒 |
| 12 | 规则求值异常上报 | 触发 `onRuleError` | 一直抛错的规则会持续偏移判定，不能静默 |
| 13 | glob `*` 不跨 `/`、`**` 跨 `/`、整体锚定、元字符转义 | 各自钉死 | 直接决定放行规则的真实覆盖面 |

## 风险与对策

| 风险 | 对策 |
|---|---|
| `sendBeacon` 无法挂起 | 默认拒发 + 告警；文档显著提示 |
| XHR 同步时序被破坏 | 记为已知限制，提供 `passthrough` 逃生配置 |
| 宽限期误判用户操作为 Agent | `graceMs` 默认取小（500ms），可配 |
| 已授权窗口过粗 | 文档写明不防御「工具行为不符合声明」 |
| Prompt injection 面扩大 | 默认拒绝兜底；执行器工具须可被权限过滤 |
| 拦截器可被绕过 | 明确非目标：防误操作，不防恶意宿主 |

## 阶段 2 实施记录

三条通道的难点各不相同：

| 通道 | 处理 | 代价 |
|---|---|---|
| `fetch` | 判定后再调原始实现 | 无 |
| `XMLHttpRequest` | `open` 记录、`send` 内部延迟发送 | **破坏同步时序**，见下 |
| `sendBeacon` | 无法挂起，需确认时拒发并回调告警 | 改变宿主既有行为 |

`form` 提交本期未做——需显式开启且与宿主表单逻辑耦合较深，留待有真实场景时再补。

### XHR 的已知限制

`send()` 必须同步返回，而判定是异步的，因此真正的发送被推迟到判定落地之后。依赖
「`send` 返回即已发出」的宿主代码会看到时序变化。这是本方案无法消除的代价，已写成
一条显式用例钉住行为，而不是留在文档里。

另一处不对称：fetch 被拒时抛 `RequestDeniedError`，XHR 被拒时**什么也不做**——它没有
可以抛错的返回值，宿主的 `error` / `timeout` 处理都不会被触发。

### 三条实现纪律的落实

1. **未命中原样透传**——保留 `this` 绑定、参数原样转发、返回值不包装。
2. **闸门自身出错时从严**——归属判定抛错按「Agent 发起」处理，策略求值抛错按「需要
   确认」处理，`confirm` 回调抛错按「拒绝」处理。三处都朝更安全的方向倒。
3. **拒绝给出可分辨的失败**——`RequestDeniedError` 而非普通 Error，调用方据此区分
   「被用户拒了」与「网络挂了」。与核心包用 `cancelled` 标记而非文案判定取消同源。

唯一的例外是 `describe()` 抛错：只降级卡片质量，不连带拒掉请求——那会把一个可用的
确认流程变成死路。
